# P2 — simplest one-pass integration and canonical-history hygiene

## Approach

Use the existing `analyze MSFT --adjustments` seam in
`src/smrik_fund/main.py:_run_adjustment_analysis()` as the only orchestration
surface. Keep the run linear and bounded:

```text
reported P&L
  -> one EdgarTools topic retrieval
  -> one exact evidence packet
  -> one Analyst resolution call
  -> one Reviewer call per returned candidate
  -> existing deterministic risk gate
  -> existing current-history resolution/application
```

The retrieval result should carry the packet text plus filing/topic metadata;
the integration passes the packet string unchanged to `run_analyst()` and
`run_reviewer()`. Do not add a generic workflow or a second SEC/evidence cache.
The known MSFT topic is `restructuring`; retrieval is selected by the current
MSFT path, not by an answer-shaped prompt or hard-coded candidate amount.

Do not add a research loop. If the chosen bounded retrieval has enough filing
context, call the Analyst once. If the Analyst still returns an unresolved
candidate or a null amount, preserve that result and send it to human review;
do not infer an amount, call the Analyst again, or copy Reviewer
`suggested_amount`. If a future minimal optional research request is retained,
the only allowed expansion is one retrieval followed by one resolution call,
with a hard call counter and no further loop. It is not needed for the known
MSFT case.

Assign run-local `A####` labels only to make review/detail artifacts readable;
the run ID remains the disambiguator. Reuse `save_analyst_result()`,
`save_reviewer_result()`, and `evaluate_risk_gate()`; preserve candidate and
review objects exactly as returned.

## Changed surfaces

- `src/smrik_fund/main.py`: replace the frozen-file-only input with the one
  retrieval call, validate packet evidence IDs before model-output persistence,
  pass filing metadata into run/manifest artifacts, and keep the existing
  Analyst → Reviewer → gate → application order.
- `src/smrik_fund/ingestion/adjustment_analysis.py`: change only if a strictly
  minimal optional research-request field is required by the selected retrieval
  contract. Prefer no schema change for the first MSFT path.
- `src/smrik_fund/ingestion/statements.py` or a small clearly named filing
  retrieval module: expose only the concrete EdgarTools filing/topic operation
  selected by the retrieval proposal; no search framework.
- Focused tests: prove one retrieval/one Analyst resolution call, exact packet
  identity, unknown-ID fail-closed behavior, null-amount preservation, and
  history/application behavior using a temporary output root.

Persistence remains the existing Markdown/JSON/CSV layout. The run manifest
should reference packet, filing accession, Analyst JSON, Reviewer JSON, and
gate results rather than embedding long evidence in CSV.

## Invariants

1. Filing content is obtained through EdgarTools. No web text, reconstructed
   prose, vector search, RAG layer, or duplicate raw-filing cache.
2. The exact packet passed to every model call is byte-for-byte the packet saved
   for the run. Evidence IDs are stable and unknown Analyst/Reviewer references
   fail before persistence or application. Any display parser must not join,
   normalize, or paraphrase quoted lines.
3. Filing accession, ticker, topic, evidence path, section, and honest source
   locator are retained. A locator is not invented when EdgarTools cannot
   provide one.
4. The Analyst remains high-recall and may return zero, one, or many
   candidates. `adjustment_amount=None` stays `None`; no parent-line or YoY
   amount is substituted.
5. At most one retrieval and one Analyst resolution pass occur for this path.
   Reviewer remains one candidate per call; a Reviewer result cannot rewrite the
   candidate or start an implicit revision loop.
6. Existing gate policy remains conservative: unavailable mechanical facts stay
   `None` and fail closed. Only a gate `auto_approve` with a finite,
   non-negative amount can reach the existing application engine.
7. Reported P&L and source reconciliation are never mutated. Approved rows are
   applied only through `resolve_current_adjustments()` followed by
   `apply_adjustments()`; adjusted reconciliation remains a hard check.
8. Canonical history is append-only and changes only at an authorized state
   transition. Exploratory/uncertain candidates are represented in the run
   manifest and review JSON, not appended as `proposed` rows. Thus an
   unresolved MSFT candidate cannot become current or alter adjusted P&L.
   Existing history is loaded and preserved; no cleanup/rewrite of prior dirty
   data is part of this task.
9. If an approved row is appended, it contains the original candidate target,
   period, amount, evidence/file metadata, reviewer/gate metadata, and a unique
   version. Later resolution still selects latest version per ID before checking
   `status == approved`.

## Non-goals

- no generic retrieval abstraction, RAG/vector DB, embeddings, web fallback,
  custom SEC parser, or raw-filing duplication;
- no broad Analyst schema redesign, answer-leaking prompt, amount estimator, or
  candidate/period fuzzy matching;
- no endless Analyst/Reviewer debate, retry policy, or multi-topic batching;
- no new approval/materiality/duplicate/group policy and no weakening of the
  current risk gate;
- no human-review CLI/UI or review-state framework;
- no second adjustment engine/history repository, direct `adjustments.csv`
  writes, or mutation of reported values;
- no removal or migration of the current dirty source/test/data artifacts;
- no commit, push, or external state change.

## Risks / verification

Primary integration risk is accidentally treating retrieval output as trusted
model context while losing exact source text. Add a fake retrieval fixture that
returns a packet containing distinctive line breaks, punctuation, accession,
and locator; assert the saved packet and both model-call payloads match it
exactly. Assert a candidate citing `E99` fails before Analyst-result or history
persistence.

Primary state risk is the current path's behavior of appending every
human-review candidate to `adjustment_history.csv`. In a temporary output root,
snapshot history bytes/row count, run the unresolved Xbox fixture, and assert
history is unchanged, the manifest records `human_review`/`not_applied`, and
`adjusted_pnl` equals reported P&L. Run the same path with a fully eligible
fixture and assert exactly one approved row is appended and only that row is
applied. Re-run unresolved analysis against existing approved history and
assert the approved adjustment remains applied while history is unchanged.

Call counters should assert one retrieval and exactly one Analyst call in the
normal path; any optional research-request path must assert no more than one
retrieval plus one follow-up Analyst call. Also run focused Analyst, Reviewer,
risk-gate, adjustment-engine, and reconciliation tests, then the real
`analyze MSFT --adjustments`, Ruff on changed files, and `git diff --check`.
Inspect packet/provenance, manifest, history bytes, and reported-vs-adjusted
equality after the real run. Do not delete existing generated artifacts during
verification.

## Estimated size

Small bounded change: one concrete retrieval surface plus roughly 50–100 lines
of orchestration/metadata adjustment in `main.py`, and 3–6 focused tests (about
80–150 test lines). Prefer touching no Analyst schema code. Stop and request a
scope decision if implementation exceeds about four production/test files or
200 new production lines; that would indicate an unnecessary workflow or
retrieval abstraction.

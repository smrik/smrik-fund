# P2 — Analytical Scan LLM, schema, prompt, and persistence proposal

## Recommended approach

Add one narrow module, `src/smrik_fund/ingestion/analytical_scan.py`, containing
the scan boundary and its deterministic presentation seam:

```text
canonical analytical P&L
  -> format_analytical_pnl_for_scan(pnl) -> compact Markdown context
  -> Responses API + native Pydantic Structured Output
  -> mechanical result validation against supplied line refs
  -> inspectable JSON under the existing analysis output directory
```

Keep this separate from `adjustment_analysis.py`: Analytical Scan is a new
read-only attention-allocation role, not an Analyst/Reviewer adjustment role.
It receives only the formatted context; it does not receive filing text,
retrieval results, adjustment history, adjusted P&L, or outside company facts.
The formatter reads the existing P&L and never recalculates or mutates it.

Use the existing direct `OpenAI().responses.parse(...)` pattern with
`model="gpt-5.6-luna"`, the existing reasoning-effort default, and a small
Pydantic response model. No provider, agent, cache, or orchestration layer.

## Exact maintained surfaces

Production:

- Add `src/smrik_fund/ingestion/analytical_scan.py`:
  - `format_analytical_pnl_for_scan(pnl) -> str`;
  - `AnalyticalScanFinding` and `AnalyticalScanResult` models;
  - `run_analytical_scan(ticker, pnl, *, filing=None, client=None, ...)`
    (client injection for tests);
  - `validate_analytical_scan_result(result, supplied_line_refs)`;
  - `save_analytical_scan_result(..., output_root=...)`;
  - concise finance-first summary rendering.
- Add version-controlled substantive prompt `prompts/analytical_scan.md`,
  with a short explicit `PROMPT_VERSION` in the module/result metadata.
- Extend `src/smrik_fund/main.py` only as CLI glue: add `--scan` and an
  `--output-root` option to `analyze`, pass the root through deterministic
  P&L/reconciliation saves, invoke the scan branch, and do not call
  `_run_adjustment_analysis` for scan-only runs. Reject `--scan` combined with
  `--adjustments` rather than risking financial-state writes.

Tests:

- Add focused `tests/test_analytical_scan.py` for formatter shape, schema
  validation, mocked Responses calls, JSON persistence, CLI isolation, and
  scan-only non-mutation.
- Keep existing adjustment, reviewer, reconciliation, and analytical-P&L
  tests unchanged except for the minimal `analyze --output-root` call-shape
  accommodation required by the CLI option.

No changes to adjustment history/application semantics, `adjustments.py`,
`reviewer.py`, filing retrieval, or the canonical P&L calculations are needed.

## Result contract and mechanical validation

Use strict extra-forbidden models at the LLM boundary:

```python
class AnalyticalScanFinding(BaseModel):
    rank: int  # 1..8
    title: str
    importance: Literal["high", "medium", "low"]
    affected_line_refs: list[str]  # exact refs printed by the formatter
    observation: str
    why_it_matters: str
    investigation_questions: list[str]  # 0..3

class AnalyticalScanResult(BaseModel):
    findings: list[AnalyticalScanFinding]  # 0..8
```

Add field length bounds and `extra="forbid"`; do not add confidence,
category, cause, adjustment, or workflow fields. After native parsing, Python
must fail closed when:

- the count is greater than eight;
- ranks are duplicated, missing, non-consecutive, or not in ascending order;
- a finding has no line reference, repeats a line ref, or references a ref not
  present in this exact context;
- a question list exceeds three.

Do not score or second-guess the model's financial judgment in Python. The
validator only enforces the response contract and referential integrity.

Line refs should be generated from stable source row order (for example
`L00`, `L01`, …), never from a label alone. The context prints the ref beside
the exact label/concept/path; this handles duplicate
`SellingGeneralAndAdminExpenses` rows and duplicate Product/Service labels.
The same deterministic ref set is passed to the result validator. Persisting
the exact context beside the result makes every `affected_line_refs` auditable.

## Prompt and context design

`prompts/analytical_scan.md` should define the role as allocating scarce analyst
attention, not explaining causes. It should state once, plainly:

- use only the supplied deterministic context and exact supplied line refs;
- compare all supplied periods, absolute movements, growth where meaningful,
  common-size intensity, bps, CAGR, margins, mix, sign swings, non-operating,
  tax, and EPS/share relationships;
- prioritize economic materiality and omit filler; zero findings is valid;
- separate numerical observation from an explanation to be answered by later
  filing research;
- ask at most three concrete investigation questions per finding;
- do not use outside Microsoft knowledge or invent causes, mappings, periods,
  values, adjustments, normalization, forecasts, valuation, or stock
  recommendations;
- copy line refs exactly and return only the declared structured fields.

The formatter should output compact Markdown with exact annual column names and
signed source values (prefer exact comma-formatted dollars; if using `$bn`, keep
enough precision or include the raw value), `N/A` for unavailable metrics, and
no invented zero. Use actual row
order and metadata to show hierarchy, e.g. separate refs/paths for
`Revenue > Product` and `Cost of revenue > Product`; do not create a taxonomy.
Display the source `GrossProfit` value as monetary Gross Profit even when its
EdgarTools label is `Gross margin`, and reserve `gross margin` for the ratio.

Use three explicit sections:

1. source P&L lines (all three annual values plus existing absolute change,
   meaningful growth, common-size, bps, and two-year CAGR where present);
2. dedicated gross/operating/pretax/net margin and ETR levels plus bps changes;
3. EPS and share rows, with values/available movement metrics but no
   common-size percentage.

Exclude abstract rows, all-period-empty rows, XBRL-only noise, and duplicate
metric aliases such as the compatibility `yoy_change_*` when the canonical
`yoy_growth_*` field is already shown. Do not deduplicate valid source rows by
concept: duplicate concepts with distinct labels or dimensions are real
lines. The current real P&L is `21 x 65`, with FY2026/FY2025/FY2024; it shows
why ordinal refs and source metadata are required.

The user message to `responses.parse` should contain only this context (plus
the normalized ticker identity if needed for metadata). Use
`text_format=AnalyticalScanResult`; never request loose JSON or add a repair
parser.

## Persistence and CLI behavior

Persist one normal inspectable artifact:

```text
<output_root>/MSFT/03_output/analysis/analytical_scan_<run_id>.json
```

Suggested top-level shape:

```json
{
  "metadata": {
    "ticker": "MSFT",
    "company_name": "...",
    "filing_accession": "...",
    "run_id": "...",
    "model": "gpt-5.6-luna",
    "reasoning_effort": "...",
    "prompt_version": "analytical-scan-v1",
    "schema_version": "analytical-scan-result-v1",
    "timestamp_utc": "..."
  },
  "context": "...exact formatter output...",
  "result": {"findings": [...]}
}
```

Take company/accession from the attached EdgarTools filing when available;
otherwise preserve explicit nulls rather than inventing identity. Use the same
run ID in metadata and filename. `output_root` must be honored everywhere so
tests and callers cannot accidentally write the real `data/` tree.

`analyze MSFT --scan` may rewrite deterministic `analytical_pnl.csv` and
`reconciliation_checks.csv`, and should show reconciliation warnings first.
Then print rank, importance, title, observation, why-it-matters, and compact
question text. It must not invoke discovery, Analyst adjustment calls,
Reviewer calls, adjustment history writes, adjusted P&L writes, or adjustment
manifest generation. Existing `--adjustments` behavior remains unchanged.

## Invariants and non-goals

- Canonical `prepare_pnl` remains the only accounting/metric calculation path.
- Reported signs, missing values, source periods, hierarchy metadata, and
  reported-vs-adjusted separation remain intact.
- Scan is observational and prioritization-only; no financial state changes.
- Context is bounded, deterministic, inspectable, and sufficient to replay the
  exact structured call; no filing retrieval or RAG.
- Normal `pytest` never creates a live OpenAI client or makes a network call;
  all LLM tests inject a fake `responses.parse` client.
- No UI, database, taxonomy, provider abstraction, background workflow,
  forecast, valuation, recommendation, or adjustment-history integration.

## Risks and verification

Main risks are line-reference hallucination, hierarchy ambiguity from duplicate
labels/concepts, ratio/sign distortion, prompt drift, and accidental
scan-to-adjustment coupling. Tests should snapshot representative context and
assert exact refs, three periods, R&D metrics, sign-crossing N/A growth/CAGR,
Product hierarchy, GrossProfit-vs-margin wording, excluded abstracts/noise,
and no common-size EPS/shares. Schema tests cover valid zero/eight findings,
over-eight, duplicate/non-ordered ranks, unknown refs, and forbidden extras.

Mocked-call tests should assert native `text_format`, model/reasoning values,
absence of `NaN`, and that the system prompt does not contain fixture facts.
Persistence/CLI tests use a temporary output root and byte-compare existing
history/adjusted outputs (or assert they are absent). Run the focused scan
tests, analytical-P&L/reconciliation/adjustment/reviewer regressions, full
pytest, Ruff on changed Python, `git diff --check`, then inspect the final
diff/stat. If credentials permit, run `analyze MSFT --scan` into an isolated
root and manually compare context/result to the current P&L; sanity checks are
large FY26 other-income movement, gross-margin compression vs operating-margin
expansion, declining R&D/S&M intensity, Product/Service mix, pretax expansion,
and higher FY26 ETR. These are review checks, not prompt-seeded answers.

## Size estimate

One new Python module (~220–320 lines), one substantive prompt (~50–90 lines),
one focused test module (~250–400 lines), and a small `main.py` CLI patch
(~30–60 net lines). This is roughly 2 production files plus the CLI and stays
inside the milestone warning; no schema/provider framework is warranted.

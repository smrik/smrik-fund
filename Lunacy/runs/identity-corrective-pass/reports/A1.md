# A1 — identity corrective pass adversarial review

Status: DO NOT MERGE. Two concrete correctness gaps remain.

## Findings

### A1-1 [P1] label drift makes an approved adjustment unapplicable

`_target_row_key()` correctly returns the same unique-concept key after a label
rename (`src/smrik_fund/main.py:173-249`), and identity lookup returns `replay`.
However, newly persisted rows still store the old `target_line`
(`src/smrik_fund/main.py:1406-1418`), while `apply_adjustments()` resolves only
that old label/concept (`src/smrik_fund/ingestion/adjustments.py:194-207`).
On a P&L whose label changed from `Research and development` to `Engineering`,
the v2 row replays but final application raises `KeyError: target line
'Research and development' was not found in P&L`. The advertised unique-concept
label-drift stability therefore does not survive the real apply path.

### A1-2 [P1] public adjustment engine still grants legacy approved authority

The main analysis path filters through `_canonical_history_frame()`, but the
public deterministic boundary does not. `resolve_current_adjustments()` selects
any `status == approved` row before identity/schema validation
(`src/smrik_fund/ingestion/adjustments.py:65-97`), and `_current_approved_adjustments()`
then applies it (`:156-190`). A full legacy row with no v2 identity but with
`target_line`, `period`, `item_amount`, and direction is accepted and changes
the P&L when passed to `apply_adjustments()`. This is a bypass of the
"unknown effective legacy fails closed" invariant outside the CLI's private
filter.

### A1-3 [P2] unknown identity versions are treated as harmless legacy

`_validated_history_identity_rows()` only recognizes a v2 marker or no marker;
an `economic-adjustment-v3` candidate identity with `status=proposed` or
`rejected` falls through to the inert-legacy branch (`src/smrik_fund/main.py:365-423`).
Observed result: `_history_identity_complete()` is `True` and lookup returns
`new`. Unknown-version/corrupt history should fail closed rather than minting a
new ID on that row-period.

### A1-4 [P2] malformed v2 identity objects with extra fields are accepted

`_identity_components()` checks required fields but not the exact v2 object
shape (`src/smrik_fund/main.py:309-324`). A v2 identity containing an extra
`surprise` field is accepted as canonical; history validation returns `True` and
lookup returns `replay`, so the malformed row can retain application authority.
The contract says v2 contains only company, fiscal period, target row key, and
item key (plus its version marker).

## Risk matrix

- R1 harmless proposed/rejected legacy blocking v2: PASS. Such rows are skipped
  by `_validated_history_identity_rows()` and excluded from the canonical frame.
- R2 legacy re-gaining application authority: FAIL via A1-2 (public engine
  bypass); the private analysis path is guarded.
- R3 unknown approved legacy silently ignored: PASS in the analysis path: lookup
  is `identity_unresolved`, no ID/history append/approval/effect. A1-2 remains
  the unguarded direct-engine route.
- R4 malformed v2 mislabeled/accepted: FAIL via A1-3 and A1-4.
- R5 label drift changing unique-concept identity: helper PASS, end-to-end apply
  FAIL via A1-1.
- R6 duplicate-concept rows collapsing: PASS for covered cases; distinct
  metadata keys are used and no safe selector yields a fail-closed error.
- R7 migration/registry/taxonomy/fuzzy infrastructure: none observed. The
  target-row-key helper is required by the v2 contract; no migration/rewrite was
  added. Complexity is concentrated in one validation helper, not a parallel
  subsystem.

Read-only review of final working-tree code and O1's terminal report. Focused

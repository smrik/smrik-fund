# P1 — bounded Reviewer recurrence + deterministic grouped summary

## Recommendation

Choose **D: the smallest combination of A and C**:

1. Make one narrow Reviewer-prompt improvement: when the supplied packet
   contains other fiscal periods, prior-period effects, repeated amounts, or
   mixed-driver parent-line language, require the Reviewer to state that fact
   in its existing `concerns`/`note`. It must distinguish recurring evidence
   from a conclusion that the item is normalizable. Keep the current
   `ReviewResult` schema unless an eval proves a structured recurrence field is
   necessary.
2. Add a pure, deterministic human-facing grouping/presentation step over the
   existing manifest candidate, review, and gate records. Group only exact
   normalized `(topic, target_line, sub_item)` keys within this run. This is a
   display grouping; it does not merge candidate IDs, assign `group_id`, alter
   `apply_adjustments()`, or change approval policy.

Persist the resulting compact object as `normalization_summary` in the
existing `adjustment_run_<run_id>.json` manifest and print the same compact
view at the end of `analyze MSFT --adjustments`. Keep the existing evidence,
Analyst JSON, Reviewer JSON, candidate records, reconciliation files, and
history semantics unchanged.

This gives the user one useful conclusion surface without making a new model
call an implicit approval or accounting engine. It also directly addresses the
current run's visible weakness: the three tax-interest periods are scattered
as separate candidates, while the Reviewer has no explicit instruction to
challenge recurrence/related-period treatment.

## Alternative comparison

### A — improve Reviewer recurrence/related-period reasoning

**Value:** High for financial soundness, especially the tax-interest group and
the OpenAI evidence containing FY2025/FY2024 losses. A prompt rule can force
the Reviewer to surface related periods, distinguish “appears in multiple
periods” from “normalizable,” and challenge parent-line or partial-attribution
claims.

**Limitation:** A Reviewer still sees one candidate per call. It cannot create
or merge sibling candidate IDs, and unstructured `concerns` alone are not a
safe grouping engine. A prompt-only change also cannot expose related-period
amounts that the Analyst did not return as candidates except as a Reviewer
note.

**Decision:** Include only the bounded prompt improvement in D. Do not add a
revision loop, new approval signal, or broad recurrence schema here.

### B — one cross-candidate synthesis call

**Value:** A model could write a polished group-level narrative, spot the
tax-interest recurrence, and mention related OpenAI periods in one place.

**Risks:** It adds a third financial-judgment stage and a new schema/output
contract; it can hallucinate totals, turn “primarily” into “entirely,” convert
nulls to zero, or blend financial assessment with Reviewer verdict/gate
status. It duplicates facts already in the manifest/evidence and increases
runtime/cost without improving deterministic accounting. A synthesis model
would need the same strict evidence and attribution constraints as the
Reviewer, so the apparent shortcut is another policy surface.

**Decision:** Reject for this phase. Reconsider only if deterministic
presentation fails a representative readability eval after D.

### C — deterministic grouping/presentation only

**Value:** Safest and cheapest. It can group the three tax-interest records,
show each period/amount, preserve nulls, copy the Analyst assessment and
Reviewer concerns, and show exact gate/application state. It adds no new
financial judgment and leaves mechanics untouched.

**Limitation:** It cannot ask the Reviewer to challenge recurrence. It also
must not infer the OpenAI dilution allocation, XBOX amount, or divestiture
amount from prose or parent-line deltas.

**Decision:** Necessary base, but combine with A so recurrence is explicitly
challenged rather than merely displayed.

### D — minimal A+C (recommended)

Use Reviewer prompt text for the missing cross-period/attribution challenge,
then use deterministic code for grouping and output. No new model call, no
new workflow state, and no change to the gate. This has the best
financial-soundness-to-scope ratio for the live case.

## Summary contract and changed surfaces

Add a focused helper (prefer a small `normalization_summary.py` module, or
local pure functions if keeping the current CLI surface smaller) that consumes
the already-built `records` and topic metadata. It should emit one manifest
object with fields equivalent to:

```text
groups: [
  {
    group_key,
    item,                 # topic + exact target line/sub-item
    periods: [
      {period, amount, adjustment_id, amount_basis}
    ],
    financial_assessment, # Analyst candidate.reason; not a decision
    unresolved_issue,     # candidate uncertainty + Reviewer concerns/note
    reviewer_states: [
      {adjustment_id, verdict, evidence_strength, judgment_level}
    ],
    gate_states: [
      {adjustment_id, decision, reasons}
    ],
    application_states: [
      {adjustment_id, final_status, application_status}
    ],
    why_not_automatic: [existing gate reasons]
  }
]
```

Implementation rules:

- Preserve candidate order or use a stable sort; never invent a period.
- Keep `amount=None` as JSON `null` and display it as `N/A`/unresolved. Never
  sum nulls, substitute a parent-line change, or use `suggested_amount`.
- Show amounts per period. Do not produce a cross-fiscal-year “group total”
  that could imply a single-period accounting adjustment.
- Use exact normalized strings only for grouping; no fuzzy topic/line mapping.
  Different topics remain different display groups even if they share a line.
- `financial_assessment` is the Analyst's stated financial view. Reviewer
  concerns are an unresolved challenge, not an overwritten assessment.
- Keep `reviewer_verdict`, `gate_decision`, `final_status`, and
  `application_status` in separate fields. `revise` is not `rejected` or
  `approved`; `human_review` is not an accounting application.
- Carry existing gate reasons unchanged (possibly with a short display label
  beside the machine reason). Do not calculate new materiality, duplicate, or
  approval policy as part of presentation.

`reviewer.py` should receive only the existing candidate, reported P&L, and
exact evidence packet. Add prompt instructions such as:

> If the packet states amounts or effects for other periods, or says an item
> occurred in a prior period, explicitly describe the related-period evidence
> and whether recurrence/recognition timing is supported, contradicted, or
> unclear. Repeated disclosure is not proof that an item should be normalized.
> “Primarily related” is partial attribution; do not treat the whole cited
> aggregate as attributable to the named sub-item. Do not rewrite the
> candidate, fill a null amount, or make the gate decision.

The main CLI should call the summary after all Reviewer/gate records are
assembled, persist it only in the existing run manifest, and print compact
group rows. Existing detailed artifacts remain the audit trail.

## Financial invariants and non-goals

- Reported P&L, adjusted P&L, `apply_adjustments()`, reconciliation, and
  `adjustment_history.csv` resolution are unchanged.
- Every internal adjustment remains one exact source line and one exact
  period. Display grouping never changes application arithmetic.
- A null amount remains unresolved. XBOX and divestiture stay null; the
  `$3.1bn` R&D increase cannot become a proposed adjustment.
- OpenAI is presented as `$6.5bn` of supported aggregate OpenAI investment
  gains only. The summary must retain the “primarily” limitation and must not
  call the full amount a dilution gain or automatically normalizable.
- Tax-interest recurrence is visible as three separate periods and challenged
  as a financial-treatment question; recurrence alone does not approve or
  reject it.
- Unresolved/exploratory candidates never enter canonical history or the
  applied adjustment frame.
- No discovery/retrieval changes, taxonomy, fuzzy matching, new group IDs,
  approval/materiality policy, human-review UI, RAG/web retrieval, or generic
  reporting/workflow framework.
- No hardcoded MSFT conclusions. The OpenAI/XBOX/tax examples are proof cases,
  not runtime rules.

## Proof and expected size

Focused tests should use manifest fixtures and mocked Reviewer output to prove:

1. Six live-shaped records collapse to four exact display groups; tax interest
   contains FY2024–FY2026 rows with amounts `1.5bn/1.3bn/1.4bn` and no
   cross-year total.
2. Null XBOX/divestiture amounts remain JSON null and display unresolved;
   parent-line changes are not substituted.
3. OpenAI output preserves the aggregate amount and surfaces the Reviewer
   partial-attribution/non-recurring concern without relabeling it as an
   approval decision.
4. Reviewer, gate, final, and application states remain distinct, including
   `accept + human_review + not_applied` for FY2026 tax interest.
5. Summary persistence changes only the manifest; history and adjusted P&L
   remain unchanged when all six candidates are human review.
6. Existing Reviewer, gate, adjustment, reconciliation, and accounting tests
   remain green; the real run still reports 12 passing reported/adjusted
   checks and `reported_equals_adjusted=true`.

Expected implementation: `reviewer.py` prompt-only edit plus one focused
summary helper and `main.py` wiring, roughly 60–120 new production lines and
100–180 focused test lines. No data/config/source artifact changes.

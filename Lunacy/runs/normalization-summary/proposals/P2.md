# P2 — existing contracts, persistence, and CLI proposal

## Recommendation

Choose **C: deterministic grouping/presentation**, with a very small D-shaped
contract clarification only where needed for output labels. Do not add a second
LLM call or a new broad model schema.

Build one pure grouping/summary function over the existing manifest candidate
records. Persist its result under the existing
`analysis/adjustment_run_<run_id>.json` manifest, and render that grouped result
at the end of `analyze --adjustments`. Keep every candidate, Reviewer result,
gate result, and application result unchanged and separately inspectable.

The existing Reviewer already produces the needed judgment text in
`concerns`/`note`, while the Analyst supplies the candidate's financial
assessment in `reason`/`uncertainty`. The summary should label and carry those
fields; it must not reinterpret them. This is enough to distinguish:

```text
financial assessment = Analyst reason (plus candidate uncertainty)
Reviewer verdict      = review.verdict
deterministic gate    = gate.decision + gate.reasons
application status    = application_status
```

## Evidence from current contracts and live run

- `AnalystCandidate` (`ingestion/adjustment_analysis.py`) preserves exact
  `target_line`, `period`, nullable `adjustment_amount`, `amount_basis`,
  `reason`, `evidence_refs`, and `uncertainty`; its `extra="forbid"` contract
  is appropriately narrow.
- `ReviewResult` (`ingestion/reviewer.py`) already separates
  `verdict`, `evidence_strength`, `judgment_level`, target/period validity,
  nullable calculation validity, `concerns`, and advisory `suggested_amount`.
  Its prompt explicitly rejects parent-line attribution and says Reviewer
  output never applies or deterministically approves an adjustment.
- `evaluate_risk_gate()` (`ingestion/risk_gate.py`) is pure and returns an
  ordered decision/reason tuple. It must remain the only gate policy.
- `_run_adjustment_analysis()` (`main.py`) already retains detailed Analyst and
  Reviewer JSON, keeps unresolved/human-review candidates out of
  `adjustment_history.csv`, resolves/applies only the canonical history, and
  writes one integrated manifest. The summary belongs in that manifest, not in
  history or a second store.
- Live run
  `data/MSFT/03_output/analysis/adjustment_run_20260821T152219572413Z.json`
  has 4 retained topics and 6 candidates, all `human_review` / `not_applied`.
  A0024 (OpenAI) has a disclosed `$6.5bn` FY2026 aggregate but Reviewer
  correctly challenges “primarily related” as not proving the whole amount or
  normalization treatment. A0025 (XBOX) and A0026 (divestiture) preserve null
  amounts. A0027–A0029 show the same tax-position item across FY2024–FY2026;
  only A0027 is Reviewer-accepted, while all three remain gate-blocked. The
  grouping output makes this recurrence visible without inventing an amount or
  changing the per-period mechanics.

## Smallest proposed surfaces

### 1. One deterministic summary helper

Add a plainly named local function (in `main.py`, unless the implementation
needs a small sibling module), for example:

```python
build_normalization_summary(records: list[dict[str, Any]]) -> list[dict[str, Any]]
```

Input is the already persisted-shaped `manifest["candidates"]` list. Group only
when the relationship is explicit and safe:

1. use an existing non-null `group_id` if present;
2. otherwise use the exact `(topic, target_line, sub_item)` identity;
3. never merge different line-period candidates merely because their prose
   sounds related.

The helper must also accept the existing fail-closed records that have no
`review` or `gate` object (for example unknown evidence or Reviewer failure):
emit nullable workflow fields and carry the record's `error` as an unresolved
issue. It must not discard those candidates from the summary.

Each group keeps internal rows separate and contains only compact structured
   fields:

```text
item / topic
target_line
periods: [{period, amount, amount_basis, candidate_ids}]
financial_assessments: exact unique candidate.reason values
uncertainties: exact unique candidate.uncertainty values
reviewer_concerns: exact unique review.concerns values
why_not_automatic: exact unique gate.reasons values
reviewer_verdicts
gate_decisions
application_statuses
```

Amounts remain numeric or `null`; `suggested_amount` is not an applied amount
and should not replace the candidate amount. Preserve period strings exactly.
Do not synthesize “normalized”, “recurring”, or “approved” conclusions.

The summary should be generated after `records` are complete and before the
manifest is written:

```json
"normalization_summary": {
  "schema_version": "normalization-summary-v1",
  "groups": [ ... ]
}
```

This is run output, not canonical adjustment state. Do not add summary columns
to `adjustment_history.csv`; unresolved/exploratory candidates must stay out of
canonical history.

### 2. Compact CLI rendering

Replace the current per-candidate evidence/excerpt dump in the integrated
adjustment path with a small renderer over the same summary. Keep artifact-path
lines for Analyst JSON, Reviewer JSON, manifest, adjusted P&L, and history.
For each group print:

```text
Item / target line
Periods and supported amounts (null stays null)
Financial assessment
Unresolved issue / Reviewer concern
Why not automatic (gate reasons)
Status: Reviewer verdict | gate decision | application status
```

Do not add a new CLI command, review UI, report framework, or evidence text
renderer. Existing detailed JSON/Markdown artifacts remain the drill-down
surface. The current CLI tests that assert every evidence excerpt should be
replaced with focused assertions for grouped item, all periods, null amount,
financial-assessment label, gate reason, and status separation.

### 3. Focused tests

Add deterministic unit tests for:

- same `(topic, target_line, sub_item)` across FY2024–FY2026 groups into one
  summary while retaining three period rows and amounts;
- unrelated topics/targets do not merge without `group_id`;
- null amount and uncertainty remain null/text, never zero or an inferred
  amount;
- candidate reason, Reviewer verdict, gate decision/reasons, and application
  status remain distinct fields;
- manifest contains `normalization_summary`, while history still contains only
  approved rows and the adjusted P&L behavior is unchanged;
- compact CLI output includes the grouped summary and does not require loading
  full evidence excerpts.

Retain existing Reviewer, gate, adjustment, reconciliation, and discovery tests;
update only tests coupled to the old verbose CLI text and add one manifest
integration assertion.

## A–D comparison

### A — improve Reviewer recurrence/related-period reasoning

Not sufficient alone. The Reviewer intentionally receives one candidate and the
exact caller-supplied packet; it cannot safely infer recurrence across sibling
candidates without violating its current isolation contract. The live Reviewer
already catches the important scope errors: OpenAI “primarily related” is not
the full amount, XBOX `$3.1bn` is a parent-line increase, and tax treatment is
framework-dependent. A broader recurrence prompt/schema would add judgment
surface and tests without solving grouping/persistence/CLI output.

### B — one cross-candidate synthesis model call

Reject for V1. It adds latency/cost, a second financial-judgment authority, a
new failure/cache/persistence contract, and possible conflation of assessment
with verdict/gate/application. The four-topic artifacts already contain the
candidate reason, Reviewer concerns, and gate reasons needed for a faithful
summary. Deterministic grouping can expose recurrence and preserve exact text;
it cannot overrule Reviewer or gate state.

### C — deterministic grouping/presentation

Recommended. It solves the observable gap with one existing-manifest field and a
small renderer; it is repeatable, cheap, testable, and keeps calculation/state
semantics untouched. It also handles the live tax example naturally: three
period rows under one item with per-period verdict/gate/application state.

### D — combination

Use only the C surface plus the explicit labels above. No new Reviewer fields or
call are justified by the live evidence. Revisit A only if a fixed evaluation
shows that existing `reason`/`uncertainty`/`concerns` cannot express a required
financial assessment; such a result should be a separate bounded Reviewer task.

## Invariants and non-goals

Invariants:

- reported P&L and accounting mechanics remain unchanged;
- candidate rows remain one line/period each internally;
- periods, signs, missing values, and supported amounts are preserved;
- disclosed amount does not imply full normalization;
- “primarily related” does not become “entirely attributable”;
- Reviewer verdict is not gate decision; gate decision is not application
  status;
- only approved canonical history rows can affect adjusted P&L;
- unresolved/exploratory summary rows never enter canonical history.

Non-goals:

- no new approval/materiality/duplicate/group policy;
- no recurrence classifier, taxonomy, topic-specific mapping, or MSFT-specific
  conclusions;
- no Reviewer revision loop, extra research pass, RAG/vector/web layer, or
  second synthesis model;
- no new output file, database, history schema, command, or UI.

## Risks and proof

- **Over-grouping:** exact key and explicit `group_id` rule; test non-merge cases.
- **Deterministic overclaiming:** copy exact text and status fields; no generated
  financial prose; test “primarily related” and null XBOX fixtures.
- **Output drift:** manifest is the single summary source; test JSON/CLI agree.
- **History leakage:** assert human-review rows do not create history rows or
  application effects.
- **Scope creep:** no production changes outside the summary helper, manifest
  insertion, renderer, and focused tests expected.

## Estimated size

Approximately 50–90 production lines and 80–140 focused test lines, likely in
`src/smrik_fund/main.py` plus `tests/test_adjustment_analysis.py` (or one small
summary test module). No Analyst/Reviewer/gate/accounting changes and no new
LLM call.

# P3 — simplicity / product-quality adversary

## Recommendation

Choose **C: deterministic grouping and presentation only**. Do not add a
second LLM call, a Reviewer revision loop, a cross-candidate Reviewer state, a
taxonomy, or a new reporting framework.

The existing MSFT run already has the judgments needed for a useful compact
view. The live artifact
`data/MSFT/03_output/analysis/adjustment_run_20260821T152219572413Z.json`
contains four retained topics, six candidates, zero approvals, and six
human-review outcomes. The Reviewer correctly challenges the $6.5bn OpenAI
amount because “primarily” does not support the whole amount; it preserves
null amounts for Xbox and divestiture evidence; and it flags the FY2025/FY2024
tax treatment as unresolved. The presentation problem is repetition, not a
missing intelligence stage.

## A–D comparison

| Alternative | Judgment | Adversarial finding |
|---|---|---|
| A — improve Reviewer recurrence/related-period reasoning | Reject for now | Reviewer already sees the multi-period tax packet and challenges unsupported treatment. Making it cross-candidate-aware would duplicate grouping state, alter the one-candidate contract, and risk turning a presentation concern into approval logic. A small generic prompt clarification is acceptable only if a live run proves recurrence is not mentioned; it is not required for this output. |
| B — one cross-candidate synthesis call | Reject | Adds cost, latency, failure surface, and a second narrative authority after Reviewer/gate. A synthesis model could merge unrelated candidates or turn “primarily related” into “entirely attributable.” It would require new schema/state and would make financial assessment harder to distinguish from Reviewer verdict and application status. |
| C — deterministic grouping/presentation | Recommend | Reuse existing manifest candidate records. Group only for display by stable existing identity (topic + target line + sub-item); retain each line-period candidate, amount, reason, concerns, gate reasons, and status underneath. Recurrence is a visible deterministic flag, not a conclusion. No change to Reviewer, gate, history, or `apply_adjustments()`. |
| D — C plus a small A change | Defer | Could be a later measured refinement, but it spends model/prompt complexity before C is evaluated. If needed, add one generic Reviewer instruction to state when supplied evidence spans multiple periods; do not add a field or a loop. |

## Smallest implementation shape

- Add one local function in `main.py` (roughly 35–55 lines) that derives an
  ordered `normalization_summary` list from existing `records`.
- Group only exact normalized `(topic, target_line, sub_item)` keys. This is a
  presentation group, not a persisted `group_id` and not an economic-event
  assertion. Keep first-seen order; do not infer relatedness from keywords or
  hardcode four MSFT topics.
- Each group should expose: item/target, periods, per-period amounts
  (including `null`), candidate IDs/count, Analyst financial assessment
  (`reason`), unresolved financial issue(s) (`review.concerns`), and why it is
  not automatic (`gate.reasons` / final and application statuses). Add a
  recurrence marker only when the same display key has multiple periods.
- Store this derived list under the existing integrated run manifest (no new
  artifact or Pydantic schema). Keep full evidence, Analyst JSON, Reviewer
  JSON, and per-candidate records unchanged.
- Replace the current full Analyst/evidence dump and repeated per-candidate
  gate lines with one concise summary after processing. Artifact paths remain
  available in the manifest. Do not change `adjustment_history.csv` behavior.

Estimated production delta: **+45–75 lines net** (including compact CLI
formatting; deletions of verbose output may offset additions), one focused
test block of roughly **40–70 lines**. No new module/dependency.

## Invariants and non-goals

- Null amounts remain null; no amount is summed when any contributing amount
  is null unless the display explicitly shows the known values separately.
- A repeated period is shown as recurrence/coverage, not declared recurring,
  normalizable, or non-normalizable.
- Financial assessment (`reason`) remains distinct from Reviewer verdict,
  deterministic gate decision/reasons, final status, and application status.
- Unresolved or exploratory candidates never enter canonical history; the
  current MSFT run must remain zero history additions and reported==adjusted.
- No new approval/materiality policy, no group reconciliation policy, no
  topic-specific conclusions, no taxonomy, no group persistence, no Analyst
  or Reviewer schema expansion, and no revision loop.

## Qualitative real-MSFT proof

Against the existing run (or one fresh authorized run), verify:

1. Exactly four display groups appear for the four retained topics, with six
   underlying candidates and no duplicated candidate IDs.
2. The tax-interest group shows FY2024 $1.5bn, FY2025 $1.3bn, and FY2026
   $1.4bn individually, marks multi-period recurrence/coverage, and does not
   collapse them into a single amount or claim a normalization decision.
3. OpenAI shows FY2026 $6.5bn and retains the “primarily” scope limitation;
   Xbox and divestiture show unsupported amounts as `null`, never zero.
4. All six records remain `human_review`/`not_applied`; no new canonical
   history row appears; adjusted P&L equals reported P&L and both
   reconciliation summaries remain 12 PASS / 0 FAIL / 0 SKIPPED.
5. CLI output is one compact group-level block with no full evidence excerpts
   or repeated Analyst/result sections; detailed paths remain in the manifest.

Focused tests should cover: same-key multi-period grouping, null preservation,
non-merging of different target/sub-item keys, status/gate-reason preservation,
and no history write for unresolved or human-review records. Then run the
existing Reviewer/gate/accounting regressions, Ruff, `git diff --check`, and
the informed live MSFT command.

## Risks / proof obligations

The main risk is deterministic grouping being read as an economic group. Label
it explicitly as a presentation summary and use conservative exact keys. The
second risk is CLI truncation hiding caveats; keep the assessment and first
unresolved issue visible, with full records/artifacts as the detail path.
Reject any implementation that adds a synthesis model, a cross-candidate
schema, hardcoded MSFT topic names, or changes gate/history/application
semantics merely to improve wording.

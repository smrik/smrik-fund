# P1 — bounded neutral discovery context and minimal topic contract

## Approach

Use exactly one neutral discovery call before topic retrieval. Give it:

1. a compact, deterministic projection of the analytical P&L; and
2. a small set of filing passages selected from P&L-linked labels and
   comparative language, without using the known restructuring/XBOX case.

The discovery call returns at most five plausible research topics. Each topic
then supplies the search query or queries for the existing exact EdgarTools
retrieval path. Discovery is a high-recall research index, not an approval or
accounting step. The existing Analyst candidate schema remains the resolution
schema after retrieval.

Recommended minimal Pydantic boundary:

```python
class DiscoveryTopic(BaseModel):
    name: str
    likely_target_line: str | None = None
    queries: list[str]
    rationale: str


class DiscoveryResult(BaseModel):
    topics: list[DiscoveryTopic]
```

Local validation should require 0–5 topics, 1–3 short non-empty literal
queries per topic, bounded string lengths, and no extra fields. `name` and
`likely_target_line` are hints only; the real P&L target is validated later by
the existing exact Analyst/reviewer/gate path. Do not add amount, period,
confidence, category, materiality, evidence IDs, status, group, or workflow
fields to discovery.

Queries should be plain filing phrases. Retrieval can escape them for the
existing regex/exact-source machinery, retaining the useful property that
every retrieval query originated in discovery output. If a query is too broad,
ambiguous, or produces no unique source match, fail that topic closed and keep
the topic as an exploratory artifact; do not retry or silently choose a best
hit.

## Context-strategy trade-offs

| Strategy | Evidence from live MSFT | Strength | Failure mode | Decision |
|---|---|---|---|---|
| Whole filing | 360,918 chars / 3,284 lines | Maximum recall; no selection assumptions | ~90k-token payload, high cost/distraction, likely context-limit risk; mixes boilerplate, risk factors, notes, exhibits | Reject for V1 discovery |
| Headings/sections | 603 chunks; broad MD&A loc 177–214 is 14,285 chars; section objects lack semantic titles | Keeps contiguous filing context and nearby contradictions | Selection depends on loc/page layout; broad range includes segment and unrelated discussion; heading search is ranked and often broad (e.g. “Effective Tax Rate” returns 54 hits) | Fallback when a topic needs surrounding context, not default discovery input |
| Deterministic P&L-linked passages | Eight neutral chunks, 4,391 chars / ~1.1k tokens, selected from actual P&L labels plus comparative cues | Small, inspectable, filing-grounded, neutral, reproducible; includes drivers without preselecting a candidate | Can miss a disclosure not linked to a face-P&L label; one broad/ambiguous label may produce no unique chunk | Recommend for the one discovery call; record omissions and let topic retrieval fetch exact evidence |

The recommended builder should operate only on the current P&L and filing:

1. Keep non-abstract, non-dimensioned rows with a usable `label` or
   `standard_concept`.
2. For each row, search bounded filing sections for the label (or a
   deterministic label variant) plus neutral comparative cues such as
   `increased`, `decreased`, `included`, or `rate`.
3. Preserve the original contiguous section text, filing `loc`, and source
   identity. Do not search for `restructuring`, `XBOX`, a gold target, a known
   dollar amount, or any answer-shaped phrase.
4. Deduplicate by `(filing accession, loc, source text)` and cap total context
   by a small character budget (the observed eight-chunk set is 4,391 chars).
   Stable source order should win; no relevance ranking or taxonomy is needed.

For the discovery prompt, include only the compact P&L signals and the bounded
passage list. Include filing accession/form/period as factual identity if
needed for artifact provenance, but do not pass the existing restructuring
packet, `tests/msft_restructuring_gold.md`, prior Analyst output, adjustment
history, or candidate-specific search terms.

## Invariants

1. Exactly one discovery model call. It returns 0–5 topics; there is no retry,
   debate, or open-ended research loop.
2. Discovery sees only the analytical P&L plus bounded neutral actual-filing
   context. No Xbox/restructuring/gold/evidence-answer hint is hardcoded in
   the prompt or context selection.
3. Every retrieval query is copied from a retained discovery topic. The
   existing EdgarTools search/text path remains the source of exact excerpts.
4. Duplicate topics/queries/hits are collapsed locally and deterministically;
   no cross-topic taxonomy, global ranking, or automatic merge is introduced.
5. A missing/ambiguous search result fails closed for that topic. No fuzzy
   source selection, inferred amount, target normalization, or period invention.
6. Topics carry no amount/evidence/status fields. Resolution candidates retain
   the existing minimal Analyst schema, including `adjustment_amount=None` for
   unsupported amounts.
7. Each retained topic receives one exact retrieval pass, then one Analyst
   resolution call per retrieved packet, one Reviewer call per resolved
   candidate, and the existing deterministic gate. No implicit retries.
8. Exploratory discovery/research artifacts may be persisted, but unresolved,
   duplicate, or human-review candidates do not enter canonical history or
   current adjustments. Existing history bytes remain unchanged unless the
   existing authorized approved transition occurs.
9. Reported P&L, signs, missing values, filing periods, and provenance remain
   unchanged. Approved amounts flow only through the existing adjustment engine.

## Non-goals

- Whole-filing prompting, embeddings, RAG, vector DB, web/custom SEC search,
  provider framework, workflow engine, or autonomous browsing.
- A generic cross-company/topic taxonomy, confidence/materiality model,
  candidate deduplication framework, or provenance graph.
- Replacing EdgarTools search or inventing a second parser/cache.
- Discovery of final adjustment amounts, approval decisions, or history rows.
- Analyst/Reviewer prompt redesign beyond passing the selected exact packet.
- Multi-call research/revision loops, parallel topic batching inside one model
  call, or retries after ambiguous retrieval.
- Cleanup of unrelated dirty worktree changes, generated artifacts, commits, or
  external writes.

## Risks / proof

The main risk is hidden answer leakage through context selection. Capture the
discovery request in a fake-client test and assert it contains P&L fields and
neutral filing passages but not `XBOX`, `restructuring`, the gold fixture,
existing evidence IDs, or known candidate amounts. Assert that changing the
current topic/evidence fixture does not change the neutral context builder.

Prove context determinism with the live MSFT shape: same filing accession and
P&L produce the same ordered loc/text set and the same bounded character cap.
Prove retrieval reuse with a fake filing: every retrieval query must equal a
query emitted by discovery; exact source text, accession, loc, and line/offset
metadata must survive unchanged. Return zero and duplicate hits in fixtures
and assert that only the affected topic is unresolved, with no best-hit pick.

Use counters to assert one discovery call, no more than five retained topics,
one retrieval per retained topic, one resolution Analyst call per retrieved
topic, and one Reviewer call per resolved candidate. Add duplicate-topic and
duplicate-hit fixtures; preserve first stable occurrence and do not merge
unrelated topics.

Run the focused discovery/retrieval/integration tests, existing Analyst,
Reviewer, risk-gate, adjustment, and reconciliation tests, Ruff on changed
code, `git diff --check`, and the real read-only `analyze MSFT --adjustments`
path when credentials/network are available. Inspect discovery/run manifests,
packets, candidate null amounts, and history bytes. The live inspection above
already confirms the actual MSFT filing and context sizes; no API discovery call
was needed to establish the selection recommendation.

## Estimated size

Small bounded change: one local discovery module (roughly 70–120 production
lines), narrow packet parameterization/orchestration (roughly 60–100 lines),
and 100–180 focused test lines across at most 4–5 files. No Analyst schema or
history-engine rewrite. More than four production/test files or roughly 200
new production lines indicates taxonomy/framework creep and should stop for a
scope decision.

# P3 — Xbox-independent discovery and evidence-integrity proof

Scope: prove that the known Xbox-related MSFT topic is surfaced from the
actual filing plus neutral P&L context, then preserve the existing exact
evidence, gate, application, and history contracts. Phase 1 remains read-only
apart from this proposal.

## 1. Approach

### Recommended context

Use a deterministic, symmetric hybrid: filing section headings plus bounded
windows around every displayed P&L line label in the actual filing's MD&A /
results sections. Generate windows from the supplied P&L labels and fixed
source offsets only. Do not select a window because it contains a known topic,
sub-item, amount, evidence ID, or gold answer. Preserve raw filing text in the
context; the model may naturally see ``XBOX`` because it is in the source.

| Context | Benefit | Independence / cost risk | Decision |
|---|---|---|---|
| Whole filing | Highest recall; no retrieval selector | Very large, repetitive, expensive, and hard to audit; many unrelated Xbox mentions can drown financial passages | Reject for V1 |
| Fixed headings/sections | Bounded and provenance-friendly; no answer query needed | A whole MD&A section can still be noisy and can omit a relevant passage if section extraction is incomplete | Accept only as a fallback/context supplement |
| P&L-linked passages | Small, auditable, symmetric across lines, and directly tied to analytical anomalies | Can miss a disclosure that uses different wording; exact-label matching can be sparse | Use as the primary context |

The context builder must receive only the analytical P&L, filing identity, and
bounded actual-filing text. It must not read the frozen
``restructuring.md`` packet, `tests/msft_restructuring_gold.md`, prior
analysis/review artifacts, or adjustment history. A missing context slice is
reported; it does not trigger a known-topic fallback.

### Discovery contract and sequential flow

- Make exactly one discovery model call. Its minimal structured result is a
  list of at most five topics (zero is valid), each containing a short name,
  optional likely target line, one concise search query or a tightly bounded
  query list, and a short normalization-research rationale. Do not add a
  taxonomy, confidence score, workflow state, amount, evidence refs, or
  approval fields.
- Locally normalize and collapse duplicate topics/queries deterministically,
  while retaining the original entries and a `collapsed_into` reason in the
  discovery artifact. Do not ask the model to deduplicate or retry.
- For each retained topic, execute one bounded retrieval pass using only the
  query string(s) in that topic's discovery result. Then render an exact packet
  from the filing text with stable IDs, accession, source, section, and honest
  line/offset locators. No hardcoded query or topic fallback is permitted.
- Run one resolution Analyst call per retained packet, one Reviewer call per
  resolved candidate, and the existing deterministic gate. There is no
  pre-retrieval Analyst call, open-ended search, retry, or revision loop in
  this path.
- Persist one discovery/run manifest containing every topic and status,
  including duplicate, no-match, retrieval-failed, Analyst-empty,
  null/unresolved, human-review, and approved outcomes. Additional discoveries
  must remain inspectable even when they do not become adjustments.

## 2. Changed surfaces

- Add one small discovery boundary (a local module or equivalent existing
  module seam) with a strict Pydantic result schema, neutral versioned prompt,
  input-context builder, deterministic topic/query collapse, and one-call
  enforcement. Keep the prompt free of MSFT answer hints.
- Extend `src/smrik_fund/ingestion/filing.py` to accept discovery-originated
  queries and keep the current exact-substring/identity validation. The new
  path must not import or call the current `RESTRUCTURING_SEARCH_QUERIES`
  (lines 14–19) or `retrieve_restructuring_evidence`; those are direct hidden
  Xbox/restructuring seeds today.
- Narrow `src/smrik_fund/main.py` to orchestrate discovery -> per-topic exact
  retrieval -> Analyst -> Reviewer -> gate. Replace fixed
  `restructuring.md`/topic metadata in this path with sanitized model-derived
  topic paths and explicit query lineage. Keep legacy direct callers only if
  they cannot influence the new path.
- Add focused integrity/integration coverage (implementation phase only):
  captured discovery input/call counts, query-origin enforcement, exact
  packet/provenance checks, duplicate/additional-topic recording, null/gate,
  and history/application checks. Existing Xbox fixtures may remain regression
  fixtures, but they must never be discovery input or a discovery oracle.

## 3. Invariants

1. Discovery input is exactly the reported analytical P&L (including nulls,
   signs, and periods), filing identity, and bounded actual-filing context.
   The discovery prompt contains no Xbox/restructuring wording, known dollar
   figures, expected target/period/amount, evidence IDs, packet filename, or
   gold fixture content. ``MSFT`` and source text occurrences are permitted
   only because they are actual input data.
2. An independence scan covers the discovery prompt, context selector, seed
   data, and path-specific imports. Case-insensitive matches for `xbox`,
   `restructur`, `$940`, `3.1 billion`, `31bn`, `E1`, `E2`,
   `msft_restructuring_gold`, and fixed answer-specific topic names must be
   absent from those surfaces. Legacy retrieval/tests may contain these terms,
   but the new path must not reference them.
3. Every retrieval query is byte-for-byte attributable to a discovery result
   after only documented whitespace normalization. Instrumented filing calls
   must show no extra query, fixed regex, seed, fallback, or retry. Maximums:
   one discovery model call, five topics, one retrieval pass per retained
   topic, one Analyst resolution per topic, and one Reviewer per resolved
   candidate.
4. Every packet excerpt is an exact contiguous substring of the selected
   filing's text. IDs are unique/stable within that packet; each item carries
   the actual accession, source attachment/path, section locator when supplied
   by EdgarTools, and source line/offset range. Unknown candidate refs,
   missing excerpts, or unhonest locators fail closed before Analyst/Reviewer
   persistence or history writes.
5. The positive live proof uses local latest MSFT 10-K accession
   `0001193125-26-323660`. Its source text contains the operating-expense and
   R&D passages at lines 1266 and 1283. A successful discovery sample must
   trace an Xbox-bearing topic/query to a packet containing the corresponding
   exact source span and accession. This is a post-run source check, not a
   prompt, seed, query, or gold input.
6. The negative leakage proof runs the same capture checks with a neutral
   filing/context in which the Xbox passages and gold packet are absent. The
   discovery input must contain no Xbox token and no fixed answer query; any
   Xbox result without source support is a leakage failure, not a successful
   discovery.
7. A topic or candidate with no separately supported amount remains numeric
   `null`; it is never coerced to zero or inferred from a parent-line change.
   Unknown/estimated basis, invalid target/period, weak evidence, unresolved
   duplicate, or any other failing/unknown deterministic condition reaches
   human review through `evaluate_risk_gate` and is not applied.
8. Only the existing authorized approved transition may append
   `adjustment_history.csv`. Exploratory, duplicate, no-match, null, failed,
   rejected, and human-review results save discovery/packet/analysis/review/
   manifest artifacts but leave history bytes and current approved state
   unchanged. Reported P&L remains immutable; adjusted P&L equals it when no
   approved row exists.
9. An approved fixture still resolves latest-version-first and uses the
   existing deterministic application/reconciliation engine once. Discovery
   does not gain a second adjustment path, direct history writer, or special
   auto-approval rule.

## 4. Non-goals

- No Xbox-specific fallback, fixed restructuring search, known-target seed,
  amount fixture, answer-based packet name, or runtime use of the gold note.
- No whole-filing LLM dump, custom SEC/search service, HTML scraper, RAG,
  embeddings, vector store, provenance graph, taxonomy, confidence framework,
  generic workflow engine, provider hierarchy, or agent tool loop.
- No fuzzy target/period matching and no amount estimation to make the known
  case pass. No auto-merge of duplicate topics or candidates.
- No rewrite of the existing Reviewer/risk-gate/application mechanics and no
  canonical-history entry for exploratory discoveries.
- No Phase 1 source, test, configuration, generated-data, or external writes;
  only this proposal is in scope now.

## 5. Risks / proof

| Attack / risk | Proof required |
|---|---|
| Hidden Xbox prompt/seed/query or accidental gold read | Static scan of the path-specific prompt/context/seed/import surfaces; run with gold packet and gold file unavailable; capture the exact discovery payload. Allow Xbox only when it is a substring of actual filing context. |
| Existing fixed retrieval silently wins | Fake filing records every search call; return three neutral discovery topics and assert each query exactly matches returned output, no `RESTRUCTURING_SEARCH_QUERIES` call, and no fourth call. |
| Model result is prior knowledge, not evidence | Positive real-filing run must show query -> packet -> exact source span -> candidate evidence refs. Context-ablation run with the source passages removed must not produce an unsupported Xbox result. |
| Context selector is answer-biased | Inspect generated selector terms: only P&L labels, universal section bounds, and fixed offsets; no known topic/amount terms. Compare the selected windows for all displayed P&L lines, not only R&D/operating expenses. |
| Exact evidence is paraphrased or locator-invented | Fake filing with known line boundaries; assert packet excerpts are contiguous source substrings, IDs/provenance are stable, and malformed/unknown refs fail before model or persistence calls. |
| Calls amplify by topics/duplicates/retries | Client and filing spies assert one discovery call, <=5 topics after bounded parsing, one retrieval pass/topic, one Analyst/topic, one Reviewer/candidate, and no retry/loop. Persist collapsed duplicates instead of silently dropping them. |
| Null amount becomes an applied adjustment | Neutral null-candidate fixture must produce Reviewer/gate human review, `not_applied`, unchanged history, and reported-equals-adjusted. A separately approved fixture proves only the existing transition applies. |
| Additional discoveries disappear | Fake discovery returns five topics spanning a duplicate, no-match, empty Analyst, null candidate, and one valid candidate. Manifest must retain all five and each status/query lineage; only the approved one can affect history/P&L. |

The live sample should use a temporary output root and inspect the discovery
artifact, per-topic packet, resolution/review artifacts, history hash, and
adjusted reconciliation. The current checked-in live artifact demonstrates
why this proof is needed: `data/MSFT/03_output/analysis/adjustment_run_20260820T201007347641Z.json`
records an initial request for Other income at line 56, but the run then forces
the fixed `restructuring` topic and Xbox packet (lines 11–40, 59, 85). That is
not independent discovery.

## 6. Estimated size

One focused discovery boundary (about 100–160 production lines), narrow
retrieval/orchestration edits in `filing.py` and `main.py` (about 50–90 lines),
and one focused integrity/integration test module (about 180–280 test lines).
Keep this to at most four production files and under roughly 200 new
production lines. If exact EdgarTools section behavior forces more code,
record the concrete limitation rather than adding a retrieval framework.

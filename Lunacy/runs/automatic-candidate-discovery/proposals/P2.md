# P2 — integration and retrieval reuse

## 1. Approach

The real-filing branch of `_run_adjustment_analysis` should become this one-way
pipeline:

```text
P&L + bounded filing context
  -> exactly one DiscoveryResult model call
  -> validate 0..5 topics, then deterministic exact-topic dedupe
  -> for each retained topic: one existing-style filing retrieval pass
  -> one Analyst resolution call per successful packet
  -> one Reviewer call per returned candidate
  -> existing deterministic gate
  -> existing adjusted-P&L/history transition
```

The current pre-retrieval Analyst call must go away on this branch. It is the
source of the present two-Analyst-call behavior. A topic has only a short name,
optional likely target line, 1--3 concise search queries, and a short rationale.
Retrieval receives only those query strings; Python must not add seed terms,
synonyms, target-line searches, or a second search pass.

Parameterize the current `filing.py` implementation rather than copying it:
keep `_search_sections`, `_source_match`, metadata extraction, packet rendering,
stable `E<n>` IDs, exact contiguous source excerpts, and packet/reference
validation. A small generic entry point such as
`retrieve_filing_evidence(..., topic, queries, output_path)` can be wrapped by
the existing `retrieve_restructuring_evidence` fixture seam. The integrated
branch must never call its fixed `RESTRUCTURING_SEARCH_QUERIES` constant.

Deduplicate before retrieval, preserving first output order. The exact local
key should be normalized `(short_name, likely_target_line, query_list)`:
trim/collapse whitespace and case-fold strings, but do not fuzzy-match, sort by
model wording, infer a taxonomy, or deduplicate candidates across topics.
Persist dropped duplicates in the run artifact so discovery is auditable.

## 2. Changed surfaces

Expected implementation surfaces (not changed by this scout):

- `ingestion/adjustment_analysis.py`: add one minimal strict Discovery topic/result
  schema and one structured-output call; retain the existing Analyst schema/call.
- `ingestion/filing.py`: parameterize the current exact retrieval path; retain the
  old fixed-topic wrapper only for existing direct tests/fixtures.
- `main.py`: discovery/context orchestration, topic dedupe, per-topic artifact
  paths, and the bounded loop. Reuse `run_analyst`, `run_reviewer`,
  `evaluate_risk_gate`, `resolve_current_adjustments`, and `apply_adjustments`.
- Focused tests should exercise fake discovery/model/filing objects and call
  counts. Existing filing, Reviewer, gate, and adjustment-engine regressions
  should remain applicable.

The no-filing frozen-packet path can remain as the narrow Task 7 test seam. It
does not have an actual filing context and therefore is not the discovery path.
The CLI real `analyze MSFT --adjustments` path must carry the filing already
attached by `build_analytical_pnl`.

## 3. Invariants and call/history behavior

Strict bounds are explicit: one Discovery model call; at most five retained
topics; one retrieval invocation per retained topic; one Analyst call per
successful topic packet; one Reviewer call per Analyst candidate; no retry,
revision loop, open-ended search, or fallback query. The total model calls are
`1 + successful_topics + returned_candidates`; a zero-topic result is valid.
Each retrieval query is used exactly once with the current `regex=True` search
and must produce one section hit and one exact source-text match. Ambiguity,
zero hits, missing accession/locator, empty packet, or unknown evidence IDs fail
closed for that topic/candidate, but are recorded and do not erase other topic
results.

Every successful packet keeps accession, source URL, topic, section/locator,
source line range, and stable evidence IDs. Candidate references are validated
against that packet before Reviewer invocation. A null amount remains null; it
is reviewed as unresolved and can never enter the approved adjustment set.
Invalid candidates are recorded as unresolved/error artifacts rather than
silently repaired.

Use collision-safe research artifacts, for example:

```text
03_output/analysis/discovery_<run_id>.json
03_output/evidence/<ordinal>_<topic-slug>_<run_id>.md
03_output/analysis/<ordinal>_<topic-slug>_<run_id>.json
03_output/reviews/<adjustment_id>_<run_id>.json
03_output/analysis/adjustment_run_<run_id>.json
```

Discovery raw output, retained/dropped-topic decisions, retrieval errors,
per-topic Analyst results, Reviewer/gate records, and status/error stage belong
in these artifacts. `adjustment_history.csv` is touched only by the existing
legitimate approval transition: append approved rows with numeric amounts and
fresh IDs. Unresolved, rejected, and human-review candidates stay in the
research/run artifacts and leave existing history bytes unchanged. Current
adjustment resolution remains “latest version first, then status approved”;
reported P&L stays immutable and adjusted reconciliation remains a hard check.

## 4. Non-goals

- No fixed Xbox/restructuring seed query in the discovery prompt, context
  builder, or integrated retrieval call.
- No whole-filing prompt, embeddings, vector/RAG layer, web/custom SEC service,
  taxonomy, confidence/ranking framework, query expansion, or provider layer.
- No fuzzy target-line mapping and no Python-generated adjustment amount.
- No candidate cross-topic dedupe; preserve separate evidence/provenance and let
  the existing duplicate-risk/gate behavior decide.
- No automatic Analyst revision after Reviewer `revise`; route it to human
  review, consistent with this task's no-loop budget.
- No new canonical history schema or separate adjustment engine.

## 5. Risks and proof

The highest-risk regression is hidden-answer dependence. Tests should assert
that the Discovery system prompt and synthetic context contain no Xbox, amount,
candidate, evidence-ID, or fixed-query hint, and that each retrieval query is
present in the Discovery output before `filing.search` is called. The context
builder should be tested with a filing whose text changes: no source text means
no fabricated context or query.

Use a fake client and filing to prove the call contract: 0, duplicate, and five
topic outputs; exact `responses.parse` counts; one `search` call per emitted
query; one Analyst per successful packet; one Reviewer per candidate; and zero
calls after a retrieval/reference failure. Verify first-occurrence dedupe is
stable and does not collapse distinct topics.

Evidence tests should retain exact source lines and accession/locator metadata,
reject ambiguous or duplicate source matches, and prevent an unknown reference
from reaching Reviewer/history. Artifact tests should show all discovered topics
including retrieval/Analyst failures. History tests should prove that an
unresolved multi-topic run does not rewrite `adjustment_history.csv`, while a
patched eligible gate appends only approved candidates and the existing
application/reconciliation path produces the expected adjusted P&L.

## 6. Estimated size

Small vertical change: roughly 3 production files, 120--190 new lines, and
one focused integration test module or a bounded addition to
`test_adjustment_analysis.py` (about 150--250 test lines). Larger growth would
signal duplicated retrieval, a workflow framework, or a new history layer.

## Filing-context strategy trade-offs

| Option | Benefit | Risk/cost | Decision |
|---|---|---|---|
| Whole `filing.text()` | Maximum recall; trivial to obtain | Unbounded tokens/cost, answer leakage, noisy Analyst-like behavior, weak reproducibility | Reject |
| Section/heading index only | Cheapest and most neutral; no answer-specific text | May not expose enough wording for useful query generation; EdgarTools section shape must be confirmed | Fallback only |
| Deterministic P&L-linked passages | Bounded, useful filing language grounded in the actual analytical P&L; no hardcoded candidate terms | Requires a small text-window selector and can miss disclosures that never repeat a P&L label | Prefer |

Preferred context is filing identity plus a fixed small number of source-text
windows around exact labels drawn from *all* supplied P&L source rows (not a
handwritten line/topic list), with a hard character/line cap. It should use one
deterministic `filing.text()` read and no `filing.search`; source passages are
context only, not evidence IDs. If no labels match, pass an explicitly empty
filing-context section and allow zero topics; do not substitute a fixed query.
This gives Discovery enough real MD&A/statement language while keeping the
selection independent of the known Xbox case and preserving exact retrieval as
the only evidence-producing path.

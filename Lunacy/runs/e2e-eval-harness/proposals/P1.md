# P1 — Core harness proposal

## Recommended approach

- Keep a thin functional core: case definitions are plain dictionaries; core owns selection, hashes, lifecycle, artifacts, normalized result envelope, comparison, and iteration ledger.
- `run_iteration()` performs one preflight, then `run_case()` per selected case with a fresh `cases/<case_id>/` directory. A static dispatch map calls only `run_filing_case` or `run_scan_case`; no reflection/import/plugin layer.
- Case records use `case_status` (`READY`/`BLOCKED`), capability (`AVAILABLE`/`UNAVAILABLE`), product status (`EXECUTION_ERROR`/`VALIDATION_REJECTED`/`COMPLETED`), critical/diagnostic checks, normalized output, judge status, and artifact refs.
- `COMPLETED` remains product-valid when output is partial, weak, unresolved, or not-computable. Judge runs only when all critical mechanics pass; otherwise `JUDGE_SKIPPED`. Judge errors are `JUDGE_ERROR` and do not change product validity.
- Persist one authoritative `iterations/<iteration_id>.json` plus `index.md`; case directories retain `summary.md`, stdout/stderr, traceback, raw product artifacts, and SHA256 refs. Rejected structured output is `UNTRUSTED/REJECTED` only inside its case directory.
- `smrik-fund eval [TICKER]` stays a thin Typer wrapper with `--suite`, `--case`, `--baseline`, `--resume`, `--live-smoke`, `--output-root`; default output root `data/evals` prevents canonical product writes.
- `compare_iterations(current, baseline)` requires matching aggregate definition, case, rubric, check, and source hashes; otherwise returns `NON_COMPARABLE`. Comparable output uses normalized fields, check outcomes, and ordinal PASS/PARTIAL/FAIL only; never prose similarity or keep/revert automation.

## Exact maintained files/surfaces

- Add `src/smrik_fund/eval_core.py`: canonical JSON/SHA256, repository snapshot, preflight, call budget, per-case crash isolation, artifact hashing, status gating, iteration JSON/Markdown, resume, and comparison.
- Add `src/smrik_fund/eval_cases.py`: frozen case/rubric/check dictionaries and aggregate definition hash; include suite membership and explicit missing-input capability records for AMZN/GOOGL.
- Add `src/smrik_fund/eval_workflows.py`: static financial functions only. Filing calls existing `load_saved_scan`/`investigate_finding`; scan calls existing `format_analytical_pnl_for_scan`/`run_analytical_scan`/validator. Both receive an isolated product root and return domain-normalized fields plus check records.
- Add `prompts/eval_judge.md` and a small Pydantic judge schema (`dimensions[]`, fixed IDs, ordinal verdict); use gpt-5.6-terra, high reasoning, native Structured Outputs, default sampling.
- Add `tests/test_eval_harness.py` for discovery, mocked lifecycle, crash isolation, gating, rejected capture, normalization, comparison/drift, resume/state isolation, optional smoke seam, and scan reuse. Add only a thin `eval` command to `src/smrik_fund/main.py`; do not alter dirty product files.
- Layout: `<root>/<iteration_id>/cases/<case_id>/` for all case artifacts; source/scan inputs remain frozen references with hashes (copy only small fixtures). Existing `data/<TICKER>/03_output` remains untouched.

## Invariants

- Preflight runs once per invocation/suite; `HARNESS READY` is independent of case outcomes. Missing/unavailable inputs produce `CASE BLOCKED`, never invented data or a product failure.
- Record model, reasoning/config, product/judge/retry call counts, ticker/accession/period/source identity, HEAD SHA, dirty flag, tracked-diff hash, and relevant-untracked hash excluding generated eval run directories.
- Definition hash is canonical sorted JSON over every case, rubric, and check; each component hash is also recorded. Resume is allowed only for the same definition and preserves completed case records.
- One product execution per case. Catch every case exception, retain traceback and partial artifacts, and continue other cases. Never let raw rejected output enter normalized results, scoring, comparison, or canonical state.
- Critical checks determine PRODUCT VALID (`COMPLETED` plus no critical failure); diagnostic failures remain visible. Only PRODUCT VALID reaches the judge. Mechanical checks reuse existing filing/scan validators.
- The shared live budget counts attempts, permits at most six setup calls plus one transient retry, and records exact totals. No eval execution mutates `adjustment_history.csv` or other product canonical files.

## Non-goals

- No workflow engine, registry/plugin system, dynamic imports, adapter hierarchy, DSL, database, experiment tracker, cache framework, repair loop, or automatic keep/revert.
- No product behavior repair, accounting remapping, source normalization, new company inputs, prose scoring, or forced pass for unavailable AMZN/GOOGL cases.

## Size / complexity

- Target 2 new production modules, 1 judge prompt/schema surface, 1 focused test file, and a thin CLI addition; no changes to ingestion semantics. Keep core roughly 250–350 lines and workflows/definitions roughly 250–350 combined; stop if framework machinery appears.

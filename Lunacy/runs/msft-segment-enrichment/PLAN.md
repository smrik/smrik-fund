# MSFT segment enrichment — Implementation Hive

Mode: full Implementation Hive explicitly requested. Sequence: diversity -> synthesis/implementation -> fresh read-only financial/simplicity review -> parent gate.

## Phase 1 — diversity

Three independent fresh Luna scouts inspect the same project authority and all user-required current surfaces/live artifacts. Read-only except unique proposal files. Each proposes the smallest architecture-preserving end-to-end design, affected maintained surfaces, financial invariants, non-goals, risks/proof, and implementation size.

## Phase 2 — synthesis and implementation

One fresh max-effort Luna judges proposals, selects the simplest faithful MSFT-first design, implements extraction/analytics/persistence/scan context/ref validation end-to-end, adds focused tests, runs the required full matrix, and produces real old-vs-new MSFT live proof. It must stop before a material architecture/scope expansion not authorized by this plan.

## Phase 3 — read-only reviewer

One fresh xhigh Luna is the user-requested financial reviewer and Hive simplicity adversary. It is strictly read-only for source/tests/config/live outputs, answers all seven review questions, and reports only concrete defects or unnecessary complexity. Any correction becomes a separately authorized repair step.

## Phase 4 — parent gate

Parent reads terminal Control Blocks/gate evidence, inspects bounded actual final code/diff/live outputs, runs one acceptance sample, and issues PASS or DO NOT MERGE. A gate scout is added only if multiple writers, repaired integration, or conflicting terminal evidence makes compression necessary.

## Gates

- Phase 1: three independent terminal proposals.
- Phase 2: faithful real extraction, final code/tests, required checks, old/new live artifacts and comparison terminal.
- Phase 3: fresh read-only review terminal; repair reopens barrier and invalidates stale proof.
- Phase 4: final state satisfies financial fidelity, scan usefulness, safety, scope, simplicity, and verification.

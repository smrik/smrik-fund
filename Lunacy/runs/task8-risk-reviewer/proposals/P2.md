# Proposal P2 — Task 8 Risk Reviewer

## Recommendation

Add one direct sibling module, `src/smrik_fund/ingestion/reviewer.py`, and one
focused test module, `tests/test_reviewer.py`. Do not edit the Task 7 module or
wire a CLI command yet. Reuse `AnalystCandidate` from
`ingestion.adjustment_analysis`; it already preserves `adjustment_amount=None`,
the four amount bases, exact target/period strings, and evidence references.

The Reviewer should accept exactly one candidate and the caller-supplied P&L
plus evidence packet. It must not read a filing, fetch evidence, or retrieve a
different packet. The packet string is included unchanged in the single
Responses structured-output call, alongside the candidate and P&L context.

## Proposed contract

Use native `Responses.parse` with a strict Pydantic `ReviewResult`:

```python
class ReviewResult(BaseModel):
    verdict: Literal["accept", "revise", "reject"]
    evidence_strength: Literal["strong", "medium", "weak"]
    amount_basis: Literal["disclosed", "calculated", "estimated", "unknown"]
    judgment_level: Literal["low", "medium", "high"]
    calculation_valid: bool | None
    target_valid: bool
    period_valid: bool
    amount_valid: bool
    concerns: list[str]
    suggested_amount: float | None = None
    note: str | None = None
```

`period_valid` and `amount_valid` are the only small extensions to the Section 2
conceptual schema; both are directly required to expose the Task 8 wrong-period
and wrong-amount cases instead of hiding them in prose. `amount_basis` is the
Reviewer’s assessment of what the supplied evidence supports, not a mutation
of the Analyst candidate. The candidate is persisted unchanged. A
`suggested_amount` is advisory only and is never applied.

Suggested functions:

```python
run_reviewer(
    ticker: str,
    pnl: pd.DataFrame,
    candidate: AnalystCandidate,
    evidence_packet: str,
    *,
    client=None,
    model=DEFAULT_MODEL,
    reasoning_effort=DEFAULT_REASONING_EFFORT,
    evidence_ref="frozen evidence packet",
    run_id=None,
) -> tuple[ReviewResult, dict[str, Any]]

save_reviewer_result(
    ticker: str,
    candidate: AnalystCandidate,
    result: ReviewResult,
    metadata: dict[str, Any],
    output_root: str | Path = "data",
) -> Path
```

Metadata should mirror the established Analyst metadata (`ticker`, model,
reasoning effort, prompt/schema versions, evidence reference, run ID,
timestamp), while the JSON body stores the unchanged candidate and structured
review. Until Task 9 creates adjustment IDs, use
`data/<TICKER>/03_output/reviews/review_<run_id>.json`; adding an invented
adjustment identity now would couple Task 8 to the later history store.

Before the call, compare candidate `evidence_refs` with IDs parsed from the
provided packet. Unknown IDs should fail closed with `ReviewError` and must not
be persisted or sent as if supported. For IDs that exist but do not support the
candidate’s claim, the Reviewer must return `revise`/`reject`, weak evidence,
and a concrete concern. This keeps evidence scope deterministic without
teaching Python to perform financial judgment.

## Prompt and invariants

The system prompt should state:

- only the supplied candidate, P&L, and exact packet are factual inputs;
- target line and period must exactly match a real supplied P&L line/period;
- no fuzzy matching, invented mapping, or silent candidate rewrite;
- amounts are positive absolute USD magnitudes under the Task 7 convention;
- `3.1bn` in E2 is the total R&D year-over-year increase, not a disclosed
  Xbox impairment amount; it cannot support a `$3.1bn` impairment adjustment;
- `null` amount plus `unknown` basis is valid Analyst output when the event is
  evidenced but no attributable amount is disclosed;
- `accept` is a Reviewer verdict only, never deterministic approval.

The frozen MSFT packet contains E1 and E2. The gold candidate is:
`Research and development`, sub-item `XBOX impairment and other related
expenses`, `2026-06-30 (FY)`, amount `null`, basis `unknown`, and E1/E2. It may
be accepted as a well-supported candidate despite its unresolved amount, but it
cannot be auto-approved until the later deterministic gate. A candidate that
uses `$3.1bn` as the Xbox amount must be `revise` or `reject`, with the total-
increase/unsupported-attribution flaw identified. Wrong target, wrong period,
unsupported evidence, and disclosed/calculated amount-basis misrepresentation
must set a non-accept verdict and an explicit structured concern.

Preserve missing P&L values as JSON `null`; preserve source signs and periods.
Do not normalize, calculate, or apply an adjustment in Reviewer code.

## Tests

`tests/test_reviewer.py` should use an injected fake Responses client and cover:

1. native structured output, one call, exact candidate/P&L/packet payload, and
   no hidden file/evidence access;
2. valid Xbox candidate with null amount/unknown basis can be accepted;
3. fabricated `$3.1bn` amount is not accepted and identifies unsupported
   attribution (also assert amount-basis misrepresentation is caught);
4. wrong target, wrong period, and evidence that is absent from the supplied
   packet fail closed or return revise/reject with the relevant concern;
5. unknown structured fields are rejected and `None` survives round-trip;
6. result plus unchanged candidate/metadata persists under `03_output/reviews`.

Run focused Reviewer tests, the existing `tests/test_adjustment_analysis.py`
regression tests, Ruff on the two changed source/test files, and a supported
live MSFT path only if credentials/runtime are already available. No live call
belongs in the normal test suite.

## Non-goals

- no deterministic approval/risk gate (Task 9);
- no adjustment history, application, or P&L mutation;
- no Analyst revision loop runtime, workflow state, review queue, or CLI;
- no evidence retrieval, filing parsing, full-packet discovery, or web/RAG
  infrastructure;
- no fuzzy target mapping, fabricated amounts, balancing plugs, or provider
  abstraction;
- no changes to existing Task 7 files/tests unless a later owner proves an
  integration requirement.

## Risks and open decisions

- Section 2 names review files with an `<adjustment_id>`, but Task 7 has no ID;
  the run-only filename above is the smallest reversible Task 8 choice.
- The documents leave full-packet versus cited-evidence context as a real eval
  question. This proposal uses the exact packet supplied by the caller and
  does not add retrieval; compare scopes in a later bounded eval if needed.
- Existing Analyst artifacts sometimes cite only E2 while the gold fixture
  requires E1 and E2. Reviewer tests should use the gold fixture and should
  not impose a new global “all packet IDs required” rule.

Estimated size: approximately 130–170 production lines and 160–220 focused
test lines in two new files; zero required production changes outside the
Reviewer module.

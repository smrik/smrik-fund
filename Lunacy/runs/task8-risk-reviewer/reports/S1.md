# Phase 2 S1 — Reviewer synthesis and implementation

Status: PASS

## Decision

- Selected the direct two-file design common to P1/P2/P3: one candidate per native
  `responses.parse` call, caller-supplied P&L/evidence only, and JSON persistence.
- Reused `AnalystCandidate` and preserved its null amount, amount basis, target,
  period, reason, uncertainty, and evidence references.
- Kept the Section 2 `ReviewResult` fields and added only nullable `period_valid`.
  This makes the required wrong-period case explicit without adding P2's unused
  `amount_valid` field or a generic validator.
- A supported Xbox candidate with `adjustment_amount=null` and `amount_basis=unknown`
  can receive Reviewer `accept` as an identified candidate; unresolved amount is
  retained in concerns and `calculation_valid=null`. This is not final approval.
- Rejected P3's mandatory `revise`/`reject` interpretation because it conflates
  Reviewer candidate identification with the later deterministic approval gate.
  Rejected P2's run-only filename because the authority specifies
  `<adjustment_id>_<run_id>.json`; the caller supplies the existing ID.

## Changed

- Added `src/smrik_fund/ingestion/reviewer.py` (224 lines): strict Pydantic result,
  one-call payload construction, packet-ID fail-closed validation, null-safe P&L
  serialization, focused prompt, run metadata, and review JSON persistence.
- Added `tests/test_reviewer.py` (303 lines): exact payload/evidence boundary,
  null Xbox case, fabricated `$3.1bn` mixed-driver amount, wrong target/period,

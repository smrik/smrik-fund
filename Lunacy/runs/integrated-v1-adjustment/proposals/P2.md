# P2 — integrated V1 adjustment proposal

## Hard prerequisite

**SATISFIED for the integration contract.** Task 4’s deterministic engine exists in
`src/smrik_fund/ingestion/adjustments.py`: `resolve_current_adjustments()` selects
the latest version per `adjustment_id` before filtering `status == approved`, and
`apply_adjustments()` validates periods/targets/amounts, groups by line-period,
does not mutate reported P&L, recomputes subtotals, and re-runs `prepare_pnl()`.
`tests/test_adjustments.py` covers latest rejection, amount override, unchanged
inputs, multiple line-period adjustments/order independence, and negative amounts.

The engine has no CSV I/O helper, but that is not a missing accounting engine.
Integration should persist a thin history DataFrame at the existing output path;
do not add a second application/history abstraction. Existing `adjustment_history.csv`
is not present, so first-run persistence must create it and later runs append.

## Smallest reuse-first path

Extend the existing `_run_adjustment_analysis()` path in
`src/smrik_fund/main.py` (or one small glue function beside it):

1. Read the frozen `restructuring.md` packet and call existing `run_analyst()`;
   retain existing `save_analyst_result()` output and exact candidate objects.
2. For each candidate, assign a stable run-local `A####` ID and call existing
   `run_reviewer()` exactly once; persist unchanged candidate + review with
   `save_reviewer_result()`.
3. Build only the caller-supplied mechanical facts required by
   `RiskGateConditions` from the reported P&L/reconciliation checks, then call
   existing `evaluate_risk_gate()`. Keep its ordered `reasons` verbatim.
4. Write one history row per candidate (`version=1`, `origin=llm`, `status=approved`
   only for `auto_approve`; `proposed` for human review, with null amount allowed),
   plus gate/reviewer metadata. Append to `data/<TICKER>/03_output/adjustment_history.csv`.
5. Resolve/apply through existing `resolve_current_adjustments()` and
   `apply_adjustments()`; write `adjusted_pnl.csv`. Reconcile adjusted output and
   fail the run if an adjusted tie-out is not `PASS`. Human-review rows must remain
   non-approved and therefore cannot affect adjusted P&L.

Persist a compact `adjustment_run_<run_id>.json` manifest containing each candidate,
review, gate decision/reasons, `final_status`, `application_status`, and adjusted-P&L
path. This avoids placing long reasoning/evidence in CSV while making the full path
inspectable. Existing Analyst/Reviewer JSON files remain the detailed artifacts.

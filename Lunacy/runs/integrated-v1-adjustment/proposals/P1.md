# P1 — prerequisite and smallest integration

## Decision

Task 4 is present and materially usable. Do not return `DECISION_REQUIRED` or
replace the engine. `adjustments.py` already provides latest-version-first
resolution, approved-only current state, non-negative amount validation, exact
target/period checks, line-period aggregation, source-line-only application,
no mutation, and deterministic subtotal/metric recomputation. Evidence:
`src/smrik_fund/ingestion/adjustments.py:25-131`, `tests/test_adjustments.py:89-176`,
Task 4 commit `27471cd`.

It is not a complete Task 5 workflow: no CSV append/load helper or adjusted
reconciliation helper exists. That is a persistence/glue gap, not a reason to
invent another engine. Write minimal run/history artifacts directly from
DataFrames and reuse `apply_adjustments()`.

## Existing seams

- CLI: `src/smrik_fund/main.py:169-207` builds/saves P&L, reconciles, then calls
  `_run_adjustment_analysis()` for `--adjustments`.
- Analyst: `adjustment_analysis.py:34-181` (schema, call, JSON persistence).
- Reviewer: `reviewer.py:45-192` (one candidate, unchanged packet/P&L, persistence).
- Gate: `risk_gate.py:49-131` (pure decision/reasons; caller supplies facts).
- Existing tests prove Xbox null amount/non-acceptance (`tests/test_reviewer.py`)
  and fail-closed null/unknown amounts (`tests/test_risk_gate.py:85-103`).

## Reuse-first call path

Extend only `_run_adjustment_analysis()`; keep `analyze --adjustments`.

1. Read frozen `restructuring.md` once; preserve exact text and reject unknown
   evidence IDs before persistence.
2. Run/save Analyst once. For each candidate, assign `A0001`, etc.; call/save
   Reviewer with that exact candidate, same reported P&L, and same packet.
3. Build `RiskGateConditions` only from existing deterministic facts. Keep
   provisional/unimplemented facts `None` (fail closed); add no new materiality,
   duplicate, Reviewer, or accounting policy. Evaluate once per candidate.
4. Build a version-1 history frame. `auto_approve` rows have numeric amount and
   `status=approved`; human-review rows have `status=proposed`, amount null.
   Never copy `suggested_amount` into a missing Analyst amount.
5. Pass only auto-approved rows to `apply_adjustments()`; retain all candidates
   for reporting. Save adjusted P&L and call existing `reconcile_pnl()` on it.

Persist one small artifact such as
`data/MSFT/03_output/analysis/adjustment_run_<run_id>.json`, inlining each
Analyst proposal, Reviewer result, gate decision/reasons, final status,
application status, and paths to Analyst/Reviewer/history/adjusted-P&L files.
No persistence class, workflow framework, command, or stage-policy changes.

## Invariants / proof

- Reported P&L stays untouched; all arithmetic remains in `apply_adjustments()`.
- Exact target/period only; no fuzzy mapping, inferred period, subtotal target, or
  invented amount. Existing latest-first resolution remains authoritative.
- Proposed/human-review rows cannot enter the applied frame. Adjusted
  reconciliation failure is hard; source warnings remain visible.
- Run `smrik-fund analyze MSFT --adjustments` against the known packet/P&L and
  require Xbox: R&D, `2026-06-30 (FY)`, amount `null`, basis `unknown`, E1/E2,
  Reviewer `revise`/unknown with null suggestion, gate `human_review` with
  concrete reasons, preserved status, `not_applied`, and adjusted output equal
  to reported output. Add a deterministic safe fixture proving the approved
  branch reaches `apply_adjustments()`.

Expected scope: `main.py` plus ~60–120 glue/persistence lines; one focused
integration-test extension/file ~100–180 lines. Main risks: null amount enters
history, proposed row gets applied, or old Analyst-only tests silently change.
